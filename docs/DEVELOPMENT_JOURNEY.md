# Building Global News Monitor

I started GNM as a senior CMDA student at Virginia Tech. My background was in programming, mathematical modeling, statistics, and data analysis. I had come across many of the tools through coursework and my own reading. GNM was my first chance to put them together in a dashboard that other people could open on the web.

## Getting the data into a form I could explore

The first version printed a few news results to the terminal. I started with GDELT's article search API, but hit rate limits and needed consistent fields for the analysis I had in mind. I switched to the Events exports, which arrive in 15-minute files and include machine-coded actors, actions, locations, and a source link. Once I could reliably read the files and translate event codes into labels, the next question was how to keep collecting them without saving the same event twice. [Early project notes](https://github.com/fegalvan/Global-News-Monitor/blob/5d49aa4/README.md)

Once the collector worked, I needed somewhere to keep its results between runs. Working with PostgreSQL meant deciding what to save as it arrived and what to prepare for queries later. Keeping the original fields alongside a cleaned version let me query the records and still trace a result back to the source. I used a database constraint to enforce event identity and a separate checkpoint for each completed export. One early fix was getting writes and commits to behave as expected. The pipeline could finish its work without persisting the data if the transaction boundary was wrong. Making those boundaries explicit later helped the scheduler recover from a partially processed file without duplicating the rows already saved. Alembic gave me a repeatable way to apply the database changes on another machine. When I started working with locations, PostGIS let the database represent a pair of coordinates as a geographic point. The map also needed a simpler operation that came up later. Grouping those coordinates into squares let the browser show the whole world at once. [Ingestion notes](TECHNICAL_WALKTHROUGH.md#ingestion-and-checkpointing) · [Transaction fix](https://github.com/fegalvan/Global-News-Monitor/commit/e3a2c67)

## From SQL to a live site

I had used APIs from the caller’s side. Building one meant deciding what the dashboard could ask for and what it would get back. When someone selects a country in React, FastAPI checks the request, passes the country code to a SQL query, and returns the result. That was how the queries I was writing became the counts people could see on the dashboard. React kept the panels in step with the filters, TypeScript helped me keep track of which fields each panel expected, and Vite built the files that Caddy could serve over HTTPS.

Getting the dashboard onto a Linux VM in Azure meant bringing along everything it needed to run. A Docker image packaged the application with its dependencies, and Compose gave me a way to start and manage the running containers for Caddy, the API, and the collector’s scheduler together. PostgreSQL had its own managed Azure server. I used the Azure CLI to work with the cloud resources and SSH to work on the VM itself. Network rules controlled whether the VM could reach the database. Once it connected, separate database roles let the collector write records and the public API read what it needed. I used my Azure for Students allowances to keep the application online independently of my computer. At the v1.1 follow-up, the expected monthly bill was about $3.65, driven by the public IP estimate, with a $5 budget and the subscription spending limit enabled. ## What changed once I could see the data

The country and event displays exposed problems that were easy to miss in individual rows. GDELT uses different code systems for event locations and actor affiliations. `GB` in event geography means Gabon, for example, while the actor code `GBR` refers to the United Kingdom. Some valid event codes were also being lost because their leading zeros matter. The v1.1 correction recovered 9,178 country mappings and restored 5,613 valid CAMEO codes in production, keeping all 178,013 pre-switch event identities. The raw source fields made it possible to repair the normalized records from the original values. [v1.1 correction and cutover](V1.1_VALIDATION.md#production-cutover-and-measured-results)

I wanted to go back further in time without asking the database to read every retained record for each chart. Hourly summaries made that possible. PostgreSQL updates the summary in the same transaction as the normalized records and keeps export coverage separately. That lets a chart distinguish a fully covered hour with zero matching records from an hour with a missing file. In the fixed Azure follow-up requests, median analytics times went from 969 to 567 ms for 24 hours and from 1,352 to 714 ms for seven days. Those requests used the same filters at each release and included the compatibility map. [Benchmark details and limits](V1.1_VALIDATION.md#three-hour-production-follow-up)

The first map approach capped the number of cells it returned. The first v1.1 preview avoided cutting any locations out of the totals but grouped them into 15-degree squares. That made the world view too coarse. The finished map used two-degree cells at the world scale and finer cells on zoom, drawing all occupied cells on a single canvas. Automated Chromium runs helped check how the filters and viewport behaved at desktop and phone widths. [Map refinement and comparisons](V1.1_VALIDATION.md#final-refinements-and-preflight-november-24-2026)

By v1.1, changing the database meant changing a site people could already use. The migration needed a recovery plan I could rehearse before switching over. An administrator login problem needed an approved password reset while the two application roles kept their existing credentials. The backup was restored to an isolated database before the switch. A fingerprint check stopped the first attempt, leaving the old images in place while ingestion resumed. The follow-up reconciled the intervening records and verified the data before switching images. Trivy checked the images for known vulnerabilities, and I kept those findings with the test results. Working on a separate Git branch gave me room to rehearse the release, and tagging it gave me a specific version to tie those checks back to. [Security checks](V1.1_VALIDATION.md#candidate-security-gate) · [Backup and rollback runbook](DEPLOYMENT.md#v11-migration-and-rollback)

## Following the reporting behind the numbers

For v1.2, I wanted the dashboard to help someone go from a pattern in the data to coverage they could read. A trend can show which categories changed in two complete periods and open the coverage for either one. A country selected on the map opens a profile, where the selected place, category, and dates also apply to the article links. The Events export gives us the first reference GDELT recorded, so the dashboard shows the source domain and the classification from the associated record. It counts identical URLs together and keeps the original event records available. [Coverage method and limits](TECHNICAL_WALKTHROUGH.md#finding-the-news-coverage-behind-a-change)

Following those links surfaced a record I would have missed in the totals. The dashboard showed what appeared to be a diplomatic visit in Vietnam. The source was an obituary from New York that mentioned the person’s past military service. Comparing the article with the original GDELT file showed where that mistake came from. It also led me to cases our own rules had mislabelled, including a report on employers breaching a wage law that GNM classified as Cyber. [News relevance audit](NEWS_RELEVANCE_AUDIT.md)

I kept the original records available and made the source and classification easier to inspect. I tightened the category rules and tested them on separate sets of articles, which showed both fewer false assignments and some real stories the narrower rules missed. The parser now keeps GDELT’s location precision and actor affiliations. The preview recovers those fields from the original exports and updates the hourly counts for records still on disk. For older summaries whose event detail has expired, category comparisons acknowledge the change in definitions. [Quality follow-up](V1.2_QUALITY_VALIDATION.md)

Once GNM has collected enough comparable weeks, I want to see how the reporting indicator behaves during ordinary fluctuations and gaps in the feed.
