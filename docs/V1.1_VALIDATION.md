# Global News Monitor v1.1 validation

The November 24, 2026 production review supplied the v1.0 baseline. It
reported 165,282 distinct records, 149 completed exports, 52 successful
scheduler cycles, and no failed exports, missing intervals, or duplicate
records. It also reported 1.9% average VM CPU, 9.4% average database CPU,
4.3 GiB of database usage, and median analytics latency of 844 ms over
24 hours and 1.17 s over the available data in a 17-day filter. Those figures
describe the live v1.0 deployment. Every result below came from local tests.

## Synthetic PostgreSQL benchmark

The benchmark used 1,750,000 generated records in a continuous 17-day window,
with deterministic timestamps and coordinates, seven categories, a limited
country mix, and explicitly simulated complete checkpoints. Both query
versions ran against the same post-correction data and indexes on local
PostgreSQL 17.11 with PostGIS 3.7.0. Measurements use one warm-up and seven
recorded queries, `work_mem=4MB`, parallel gather disabled, and warmed
storage. They include query execution and psycopg response decoding. The
Windows test host, synthetic country cardinality and data layout, and
loopback connection differ from Azure. The 24-hour benchmark included about
103,000 records.

| Global window | v1.0 analytics with legacy map | v1.1 analytics with legacy map | v1.1 dashboard analytics | Separate v1.1 viewport map |
| --- | ---: | ---: | ---: | ---: |
| 24 hours | 319.57 ms | 103.70 ms | 3.72 ms | 111.21 ms |
| 17 days | 4,477.16 ms | 895.83 ms | 25.39 ms | 1,148.11 ms |

On the same response contract, the medians fell approximately 68% and 80%.
The test asserted exact totals, geography counts, country and category
counts, time buckets, export coverage, and legacy map cells.
The separate viewport query accounted for every valid coordinate in the
worldwide selection, including all 1,555,556 geolocated records in
the 17-day run. The dashboard can render core analytics while the
viewport request finishes. Viewport query cost still grows with the amount
of matching raw detail.

The 17-day v1.0 plan read 69,889 temporary blocks and wrote 15,034. Its
24-hour plan read 3,876 and wrote 646. The measured v1.1 rollup,
coverage, and viewport queries had zero temporary block reads and writes
on both windows. The test used the v1.0 analytics SQL from commit
`79e672f`, read from local Git history.

To reproduce from the repo root with a disposable empty database named
`gnm_bench` on localhost, use:

```bash
python -m scripts.benchmark_v11 postgresql://LOCAL_USER@127.0.0.1/gnm_bench
```

Passing `--reuse` remeasures an already seeded database.
The benchmark creates data and indexes. Allow several GiB of test disk and
time for the initial schema migration and bulk load.

## Tests and security

- The complete backend suite ran against real PostgreSQL/PostGIS, including
  code correction, rollback and re-upgrade, dedupe and retry, retention,
  exact partial-hour totals, zero-versus-missing coverage, anomaly arithmetic,
  antimeridian counts, hostname attribution, and monitoring.
- A seventh public export at 12:30 UTC was ingested directly with v1.1 using
  the scoped runtime role. The first run inserted 1,233 records and the repeat
  inserted zero. The read role returned 1,233 normalized, live, and archived
  records and could read the completed scheduler heartbeat.
- The frontend unit tests, TypeScript check, and production Vite build passed.
  Chromium on desktop and at 390 px mobile width verified map zoom and reset,
  map-to-country navigation, source details, filter combinations, pagination,
  manual refresh, and a fixed custom UTC range. A simulated export advance
  in the browser verified automatic refresh with filters preserved. A
  simulated history failure verified the error state independently of the profile.
- The Azure Compose overlay passed `config --quiet` locally. Existing-style
  role grants were exercised on PostgreSQL. `gnm_api` can read rollups and
  heartbeat state, and PostgreSQL denied its write. `gnm_ingest` can
  record scheduler state and invoke bounded cleanup. Direct aggregate
  writes by both service roles are denied. Application SQL uses parameters
  for inputs and fixed fragments for filter shapes.
- `npm audit`, `pip-audit -r requirements.txt`, and `pip check` reported
  no known vulnerabilities or dependency conflicts. A targeted tracked-file
  and Git-history secret scan found no private-key or token patterns. Scan
  the exact final Linux image digests before rollout. Deployment-specific
  TLS, firewall, and Azure maintenance verification remain in the release
  runbook.

## Resource envelope and follow-up

The 17-day synthetic data produced 39,984 populated hourly groups and
approximately 6.34 MiB of aggregate table plus indexes. The viewport covering
index used about 60.1 MiB. At 274 official codes plus one unmapped group,
seven categories, and 2,160 retained hours, the current classifier and
country dictionary permit about 4.16 million distinct hourly keys. Applying
the measured bytes per group to that saturated case gives roughly 0.65 GiB
before bloat. The bound assumes the one canonical name per code supplied by
the v1.1 normalizer. Actual production cardinality, churn, and disk usage
need monitoring. Archive retention is 90 days. Raw retention is still 17 days.

The VM, disk, Flexible Server, Caddy, IP, and network configuration stay
the same. Hosting is expected to stay around $3.65/month while existing
allowances apply. The release creates no paid service. Platform CPU,
credits, memory, storage and egress should be observed during rollout before
claiming production resource or latency improvements.

Historical coverage begins where retained details and completed checkpoints
overlap. Normal dedupe is scoped to retained rows, with expired checkpoints
preventing reprocessing of a previously handled export. A source record
reappearing in a different export after its raw row has expired cannot be
deduplicated across that boundary. Event counts and category labels depend
on source coverage and GDELT coding. Calibration of anomaly thresholds
requires real matched weeks. The viewport query remains the largest
dashboard query. After rollout, measure its high-percentile latency before
considering more spatial rollups. Historical playback was deferred.

The category audit also found that the legacy cyber heuristic can infer
cyber activity from an intelligence-sharing code without corroborating
text. Category trends should be interpreted as GNM classifications.
Review a labeled sample and migrate any future category-rule changes
consistently across raw and historical counts.

See the [technical walkthrough](TECHNICAL_WALKTHROUGH.md#v11-data-and-query-architecture)
for the score and retention model and the [deployment runbook](DEPLOYMENT.md#v11-migration-and-rollback)
for release and rollback commands.

### Candidate security gate

`sha256:da7ff42feae648dce120f07a2aabe2f4dfcb15ee076693fd3ebd469b3d9cedb0`.
The staged Caddy/frontend image was
`sha256:5bbf07b3f73cb799b7c7ce285419b61492811ffb0ad1fcaf55515ebf25b8b2d4`.

The scans found zero secrets, zero critical findings, and zero high-severity

pairs tied to Debian packages without fixes. The Caddy image had one
unfixed Go JOSE v3 advisory, CVE-2026-116587. The production Caddy
configuration only serves static files and proxies FastAPI and has no
route that parses user-supplied JWKs. Keep rescanning these images after
upstream releases. [Go JOSE advisory](https://github.com/advisories/GHSA-mgcc-cww5-fp2q)

Local `pip-audit`, `pip check`, and `npm audit` were clean. A targeted
tracked-secret scan found no matches. The v1.0 production API used
hostname-verified TLS 1.3 and a read-only PostgreSQL role. The two runtime
database accounts lacked public-schema create and administrator membership.
The database firewall listed exactly one application VM address, and
the VM restricted SSH to an operator address while exposing HTTP/HTTPS.

### Production cutover and measured results

v1.1 went live on November 24, 2026 at 17:29:44 UTC. The existing
VM, Flexible Server, DNS name, spending limit, and budget were retained.
The approved administrator password reset preserved the two runtime
role credentials and grants. The owner login was verified from the VM
with hostname-verified TLS 1.3. The new owner credential is stored in
Windows Credential Manager and was used in memory for the VM work.

A protected PostgreSQL 17 production dump restored 176,726 records to
a loopback-only disposable database. Migrating the copy produced matching
raw, normalized, live, and historical totals, and the v1.0 image could
still read the migrated schema. The live scheduler was paused for the
final pre-migration dump ending at the 17:15 UTC slot. The first cutover
halted after the schema migration when a verification command compared
an incorrect fingerprint. Its safety handler restarted the v1.0
scheduler before switching any images. The release then reconciled the
1,287 records that v1.0 ingested during that interval, validated the
backup, and checked the corrected raw identity fingerprint and all
table totals before making the image switch.

Across the initial and follow-up corrections, production recovered
9,178 country mappings and restored 5,613 valid CAMEO codes. At the
image switch, all 178,013 pre-switch raw identities were preserved
with matching normalized, live, and historical totals. Of these records,
173,083 had mapped countries, 4,842 lacked a source country, and 88
supplied an unmapped code. No event-code flags remained. The previous
API and web images are retained under local rollback tags, the original
Compose files remain available, and the pre-migration dump is protected
